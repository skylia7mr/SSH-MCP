# Codex Goal 实施提示词

在项目目录开启 `/goal`，将下面分隔线之后的全部内容作为目标。此文件是实施任务，不要求用户再次确认已确定的产品决策。

---

请在当前 SSH-MCP 仓库中完整构建并验证一个可本机使用的 SSH MCP 工具。先阅读 `docs/project-plan.md` 和适用的 AGENTS.md。按以下需求持续实施到可运行、可验收、已按阶段 Git 提交的完整系统，不停在脚手架、方案或演示数据。`docs/previews/ssh-workbench.html` 仅作为“连接侧栏”布局参考，产品必须使用真实后端数据。

## 1. 最终结果和范围

本地操作者启动工具，在浏览器中登录多个远程 SSH 账号并建立真实 SSH 连接。Codex 或其他兼容 MCP 客户端连接本地 MCP endpoint，发现当前连接，选择 session_id 提交命令，得到真实 stdout、stderr、退出码和执行状态。网页实时查看 Agent 的执行结果。

这是本机单操作者工具，“多个账号”是多个远程 SSH 账号。后端默认绑定 127.0.0.1，Docker 也只向宿主机 loopback 发布端口。不实现公网、网页多用户、租户管理、云部署、交互终端、文件管理、跳板机或 Windows SSH 兼容。网页不提供手动命令执行入口。

远程端不安装本项目程序、服务、Python 包、守护进程或持久 helper；使用已有 sshd、Linux/POSIX shell 和 sudo。明确最低远程环境依赖及实际验证的 shell，不假设任意 SSH 设备都支持完整 POSIX shell。

SSH 密码、私钥、私钥口令、sudo 密码、连接配置、任务和命令输出只在进程内存中保存。进程退出后重新登录，不做自动凭据恢复。仅用户确认过的 SSH 主机信任公钥可使用本地 known_hosts 文件保存。不引入凭据数据库或加密保存功能。

## 2. 工程要求

- Python 使用 uv 管理环境、安装依赖和运行命令；提交 pyproject.toml、uv.lock 和 Python 版本配置。
- 后端使用 FastAPI、Uvicorn、Pydantic、AsyncSSH 和官方 MCP Python SDK；核对官方稳定版本与目标 Codex 客户端兼容，锁定依赖。不要混用不同 SDK 大版本的接口，不自行重造 MCP 协议。
- 前端使用 React + TypeScript + Vite，npm 管理依赖并提交 package-lock.json。使用普通 CSS 或少量通用组件即可，不引入无需要的庞大 UI 系统。
- 用 Ruff、Python 类型检查、pytest、前端类型检查和生产构建进行适当验证；浏览器 E2E 使用 Playwright 或等效工具。
- 单后端进程、单 worker。网页 API 和 MCP 必须调用同一个 SSH 注册表和同一个任务服务。stdio 若因客户端兼容性确实需要，只作为运行中 HTTP 后端的桥接器，不建立第二份连接状态。
- 生产时 FastAPI 提供前端构建资源，网页、API、输出订阅和 MCP 同源；开发时 Vite 代理 API。提供 uv 本地启动和 Docker Compose 两条运行路径。
- 合理分离配置、认证、API、MCP、SSH、任务、host key 和 schema 模块，避免庞大的单文件实现或不必要的通用框架。

## 3. 前端：中文连接侧栏工作台

实现完整的中文界面，默认跟随系统明暗主题，普通用户无需了解内部协议才能管理连接：

1. 启动后用一次性本地配对码建立网页会话；不实现注册或用户账号系统。
2. 顶部显示工具名称、新建连接按钮、Codex/MCP 接入入口及真实后端在线状态。
3. 左侧显示 SSH 连接的别名、username@host 和连接状态，点击后右侧切换该连接；窄屏下连接列表移至上方。
4. 新建连接弹窗包括别名、主机、端口、用户名、密码或私钥、私钥 passphrase。私钥可粘贴或从浏览器选择文件，不能要求用户提供后端任意文件路径。密码输入有遮罩，不默认将 SSH 密码复用为 sudo 密码。
5. 未信任的主机必须展示算法和 SHA256 指纹，由用户显式确认。连接前校验已确认的公钥，防止探测与认证之间的 key 替换。key 变化必须拒绝，不自动接受。
6. 右侧展示连接详情、断开操作、每连接独立 sudo 开关和 sudo 密码设置/清除按钮。默认关闭；实时生效状态以服务器响应为准，请求失败时回退并解释错误。
7. sudo 密码输入提交后清空组件状态，后续仅显示“已配置/未配置”，不能读取回填密码。关闭开关默认清除该连接密码；断开和退出也释放密码。
8. 下方显示该连接的 Agent 命令记录：命令、来源、开始时间、任务状态、退出码、耗时和 sudo 使用状态。选中后分别查看 stdout、stderr、错误和截断标记；运行任务可尝试取消。
9. 输出随执行更新，用户手动向上查看时不强制滚回底部。渲染纯文本、正确处理大输出和空输出，不用 dangerouslySetInnerHTML，不执行远程 HTML 或控制序列。
10. 提供连接中、失败、已断开、无连接、无任务、后端重启等状态，以及清晰的错误恢复路径。浏览器刷新保留后端当前连接；浏览器关闭不自动断开 SSH。
11. MCP 接入入口提供 endpoint、实际验证过的 Codex 配置示例、token 首次显示/轮换。token 不放 URL、localStorage 或普通日志，固定 token 支持由环境变量提供。不要展示虚假的“已连接 Codex”状态。

网页只管理连接、sudo 策略和查看/取消任务。REST API 也不额外提供未经需要的任意命令执行入口，MCP 是命令提交入口。

## 4. SSH 与生命周期

- 支持密码和私钥认证，包含加密私钥；验证地址、端口、用户名和输入大小。
- 禁用 agent forwarding、隐式 ssh-agent、本机默认私钥探测和未经允许的 OpenSSH 配置/ProxyCommand。只使用网页明确提交的认证材料。
- 使用不含秘密的 session_id。列表和详情仅返回连接元数据及 sudo 状态，不返回密码、私钥或口令。
- 成功建连后尽快释放不再需要的 SSH 认证输入；失败时安全清理。Python 释放引用不应声称保证物理内存擦除。
- 实现连接超时、keepalive、掉线检测、状态同步、主动断开和应用关闭清理。
- 掉线后不自动重放命令；新连接使用新身份/状态，不能把旧任务误报成功。
- 不设置未说明的自动断开策略；连接总数与并发应有可配置上限。

## 5. MCP 工具和结果

主入口是 `http://127.0.0.1:8000/mcp`，端口可配置；使用 Streamable HTTP 和独立 Bearer token。按实际 SDK/客户端支持实现协议协商，不假设某一个版本固定永远兼容。

暴露六个工具：

- `ssh_list_sessions`：列出当前连接、主机、用户名、状态和 sudo_enabled；不含秘密。
- `ssh_get_session(session_id)`：查询指定连接的当前状态。
- `ssh_execute(session_id, command, timeout_seconds?, cwd?, env?, idempotency_key?)`：提交命令。短时间等待快速结果；长任务返回 run_id 和明确状态，后续通过读取工具完成。
- `ssh_get_run(run_id)`：查询 queued/running/finished/failed/timed_out/cancelled/disconnected 状态、退出码/信号和时间。
- `ssh_read_output(run_id, stdout_cursor?, stderr_cursor?, limit?)`：读取分段结果、下一游标、是否完成和截断信息。
- `ssh_cancel_run(run_id)`：尽力取消，并给出真实可验证的状态。

MCP 不允许 Agent 创建/断开 SSH 连接、启用 sudo 或写入/读取 sudo 密码。Agent 用账号现有权限执行普通命令无需逐条用户审批。

工具必须提供清楚的 schema、描述和结构化结果，使用实际 SDK 支持的方式标识工具错误。区分参数错误、未知连接/任务、连接不可用、sudo 未授权、密码未配置、认证失败、语法不支持、输出截断、超时和 SSH 故障。远程非零退出码作为正常执行结果报告，不能与传输错误混淆。

## 6. 命令任务

- 默认每次独立 exec channel，上一次的 cd/env 不延续；显式 cwd/env 使用正确的 shell 引用和环境变量名校验。
- 不在本地 shell 执行 Agent 命令。远程保留受支持 shell 的连接符、引号、管道、重定向和退出状态语义，不把整个复合命令提升为 root。
- 默认 timeout 60 秒，可配置最大 3600 秒；MCP 初始等待约 2 秒，之后用 run_id 查询。保持取消和状态转换一致。
- stdout/stderr 并行持续读取，分别硬上限 1 MiB；超限后明确截断并继续排空，不能无限累积内存，也不能等待进程完整结束后才截断。
- 默认全局运行并发 16、单连接 4、排队最多 64、总任务记录最多 1000、完成任务保留 30 分钟，均可配置；拒绝或清理策略必须明确，不能淘汰运行中的任务。
- 输出游标有明确定义；处理非法游标、UTF-8 多字节分块、无效字节、输出已过期和读取上限，保证 Agent 重复读取可解释。
- 幂等键仅对同一进程和保留期限有效，相同 key 不重复执行；不同命令使用同一 key 应报冲突。
- 任务与浏览器/HTTP 短请求生命周期分离；明确 MCP 请求取消与后台任务取消的映射，不依赖浏览器保持打开。
- 尝试发送信号、关闭 channel 并回收本地资源；不要承诺所有远端后代进程都一定停止。

## 7. sudo：重点先做可行性验证

用户已确认以下约束，不要退化为“只检测命令开头”或“有 sudo 就把整个命令提权”：

1. 每个连接独立 `sudo_enabled`，默认 false；sudo 密码仅内存保存，由网页提交，可更新/清除，不能默认使用 SSH 登录密码。
2. 开关仅由网页管理。任务入队后，在真正创建远程 channel 前重新读取最新策略，完成原子授权并记录策略版本；排队期间关闭开关的 sudo 任务须拒绝。已开始的任务使用其授权快照，不因之后关闭而中断。
3. 使用 shell 语法解析/AST，遍历所有实际 command node；不能用前缀正则、关键词搜索或 split。选择解析器前验证语法支持和许可证，锁定依赖。不得把 bashlex 等解析器声称为支持所有 Bash 语法。
4. 处理 `sudo ...`、`/usr/bin/sudo ...`、支持的 command/env 前缀，以及 `&&`、`||`、`;`、管道、括号子 shell、命令替换内的 sudo；区分 `echo 'sudo id'`、注释、heredoc 普通文本。保留原位置和 shell 语义。
5. 关闭状态下发现受策略管理的 sudo，执行前拒绝整条命令；例如 `touch file; sudo id` 不能先执行 touch。无需密码的 sudo 同样必须被开关限制。
6. 对语法错误、无法可靠解析或无法安全处理的动态提权写法明确返回 `UNSUPPORTED_COMMAND_SYNTAX`，不回退原样执行。对可识别的字面量嵌套 shell 命令，递归解析或明确拒绝；不能悄悄漏过。
7. sudo 开启时只提升原来指定的子命令。保留正常 sudo 选项的受支持范围；拒绝会覆盖受控密码通道、后台化或要求交互终端的不支持选项，给出可操作错误。不要无限等待密码。
8. 密码不能进入命令文本、argv、环境变量、远端文件、输出、日志或结果；仅通过 SSH 的受控内存数据通路提交。不要直接把密码写进被管道/重定向占用的 stdin，也不要在 NOPASSWD 或认证缓存命中时把未消费的密码送给实际命令。
9. 先在本地测试 SSH + 真实 sudo 环境做最小可行性实验，再决定远程 shell 包装和密码通道方案。分离 sudo 认证输入与命令 stdin，保留 stdout/stderr。验证多个 sudo、管道/重定向、不同 channel、密码提示无换行和跨块的情形。不要假设另一条 channel 上的 sudo -v 会授权当前任务。必要的内部 SSH 通道不等于向网页或 MCP 开放交互终端。
10. 核心验收案例包含 `printf 'data\n' | sudo tee <测试路径>`：密码需要与 pipe 的 data 严格分离，文件和输出都不能包含密码。如果某类复杂语法确实不能满足约束，应在执行前明确拒绝、测试并记录支持矩阵；这不能作为省略普通 sudo 密码和基本复合命令支持的理由。如果核心要求无法实现，先提供实验和具体冲突，再请求调整，不擅自落盘密码或安装远端 helper。
11. 无密码时可尝试无需输入密码的 sudo，需要密码则及时报未配置；错密码有有界重试和明确失败，不无限重复输入。确认服务器实际密码策略，不假设所有 sudo 都验证登录用户密码。
12. 关闭开关清除连接保存的密码；已授权运行任务可保留需要的内存快照到结束，结束后释放。错误处理、断开和退出也清理。

已确认的边界：任意远程脚本、Python 或动态程序可能间接调用 sudo；本地语法处理不是主机权限隔离，root 登录也不会降权。真实绝对禁止必须依靠远端账号/sudoers。前端用简短说明和文档表达该边界，无需逐命令免责声明。

## 8. 本地认证与防护

- 启动生成一次性配对码，在受控启动终端展示，换取 HttpOnly/SameSite cookie；配对码不放 URL 或普通请求日志，有有效期和尝试限制。浏览器刷新不要求重复输入，后端重启则重新配对。
- MCP token 与网页认证独立；可用环境变量配置固定 token，默认随机进程内 token。网页仅通过已认证流程首次展示/轮换，不回填旧 token；轮换撤销旧 token，覆盖持久 HTTP/SSE 通道的授权状态。
- 验证 Host、Origin、CSRF 和请求大小，允许实际本机 MCP 客户端无浏览器 Origin 的请求，不能误伤 Codex；拒绝不可信浏览器跨站来源。
- 认证覆盖连接/任务 API 和输出订阅。SPA 静态资源回退不能吞掉未知 API 或 MCP 路径。
- stdout/stderr 可能包含用户主动执行命令产生的秘密，不能声称通用脱敏。工具自身提交的密码和内部控制标记必须从可见结果排除，诊断日志不记录请求体或异常中的秘密。

## 9. 测试与验收：必须真实验证

自行创建本地隔离的 SSH 测试环境，不要求用户提供生产凭据，不对用户真实服务器执行测试。AsyncSSH fixture 适合协议故障测试；实际 sudo、shell、sshd 行为需要真实环境（例如测试专用 Docker 容器），不能仅 mock 后宣称成功。

必须覆盖：

- 网页通过密码和加密私钥建立 SSH；错误凭据、主机未知、指纹改变、host key 探测后的变更、超时和掉线。
- 两个不同 SSH 账号/连接同时在线，官方 MCP 客户端经真实 HTTP 完成协议建立、tools/list 和 tools/call；准确执行指定 session，返回 stdout、stderr 和退出码。不能只调用 Python 工具函数作为 MCP 集成测试。
- 长任务、分段输出、非零退出、大输出硬上限、并发/排队/保留限额、取消、超时、断开与关闭清理。
- sudo 默认拒绝、按连接隔离、正确/错误/缺失密码、免密配置和认证缓存；任务排队时切换 sudo、运行中关闭 sudo；多个 sudo 与复杂连接符。
- 至少测试：`echo ready && sudo id`、`false || sudo id`、`touch <path>; sudo id`、`sudo id; sudo id`、`sudo cat <file> | grep <pattern>`、`printf 'data\n' | sudo tee <path>`、`(sudo id)`、`echo "$(sudo id)"`、`/usr/bin/sudo id`、`command sudo id`、`env sudo id`、普通字符串/注释中的 sudo。关闭时有副作用前缀不得执行。明确嵌套 shell、动态命令和不支持选项的行为。
- 用测试专用随机 sentinel 密码验证：不在命令文本、结果、浏览器持久存储、日志或远端测试文件出现；并验证没有把密码误当作 pipe 数据。
- 未认证、错误 token、token 轮换、非法 Host/Origin/CSRF。实现真实授权检查。
- 至少一个浏览器 E2E：配对 → 指纹确认 → SSH 建连 → sudo 设置 → 外部 MCP 客户端执行 → 网页看到结果 → 断开。浏览器访问的是实际应用，不是静态草图。
- Python lint/类型/测试、前端类型与生产构建通过，uv 锁文件安装可恢复，Docker Compose 构建、启动和健康检查实际通过。
- 用真实 Codex 客户端验证 endpoint 和配置（环境可用时）。如当前环境无可用 Codex 客户端，使用官方 MCP 客户端完成实测，并在报告中区分协议已验证和 Codex 尚未实测，不能伪造验证。

## 10. 文档、启动与 Git

README 用中文清楚说明依赖、首次安装、前端构建、uv 单服务启动、开发启动、Docker Compose 启动、网页配对、SSH 登录和 Codex 接入。生产构建后用一个清楚的 uv 命令启动后端和已打包网页，不能暗中依赖另一个 Vite 进程。

补齐 architecture、configuration、mcp-client-setup、operations 和 sudo-support 文档，包含配置默认值、认证/token 轮换、host key 管理、内存保存/重启行为、任务取消边界、sudo 支持矩阵和常见故障。Codex 配置以实施时核对的官方格式为准，示例使用环境变量或占位符，不提交真实 token。提供 .env.example、Dockerfile、compose.yaml、健康检查和合适的 CI 配置。测试 SSH fixture 与生产容器分开，生产不启动测试 sshd。

过程中使用 Git 提交，推荐阶段：

1. 项目、uv/前端工具链和最终方案。
2. 本地认证、host key 和 SSH 连接管理。
3. shell/sudo 可行性验证、实现和行为测试。
4. 命令任务、输出限额和 MCP 集成。
5. 中文网页、订阅和浏览器 E2E。
6. Docker、CI、文档与完整验收。

可按实现依赖调整阶段。每个阶段完成相应验证后提交。只暂存任务相关文件；不提交秘密、.venv、node_modules、数据库、日志、known_hosts 或临时实验产物；不要 push，不重写用户历史。

规划时当前环境的 .git 是受保护的空目录，git status 失败。先复核当前环境；若需要初始化且受权限阻塞，按正常工具权限流程处理。不要删除受保护目录、转移 Git 元数据来绕过限制或伪造提交。Git 提交阻塞时继续可执行的工作，并保留清楚的差异和说明；没有实际提交就不能声称提交完成。

## 11. 工作方式和完成条件

这些产品决策已经确认。常规技术选择、可逆编辑、依赖安装、测试和阶段提交在目标范围内；无需再次询问前端栈、用户模型、凭据保存或 sudo 默认值。遵守环境实际权限，缺权限走工具正常审批流程，不能绕过。

先建立实施清单和记录，优先验证 sudo 密码与管道、真实 MCP/FastAPI 生命周期。边实现边运行有意义的测试，及时修复；不要为节省时间只写 mock、不做 E2E 或将完整功能留作 TODO。

进度更新说明已完成、发现和下一步，不刷屏。继续推进直到核心功能、验收和阶段提交完成；真正的权限/环境阻塞要明确指出，可做的独立工作继续完成。无需部署到外网，也不创建 PR 或发消息给第三方。

完成后提交交付报告：启动命令与网页/MCP 地址、Codex 配置方式、功能说明、实际运行的测试和结果、Git 提交列表、剩余限制。保留测试日志摘要以供 review。未运行的检查明确列出，不能宣称通过。只有真实可运行的系统和要求的验收已完成，才能把 Goal 标记完成。
